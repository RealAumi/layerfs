# fs-bench pair `20261019T194736Z`: LayerFS core fully through `sandbox.exec`

> **Status:** Dated campaign record.
> - **Pair: INCOMPLETE.** Two Computer rows, `stat 1000 files` and
>   `find tree`, are saturated at 2,147,483,647 ns: the frozen runner's
>   `awk printf "%d"` under mawk. Their true values are unknown, and only a
>   lower bound remains.
> - `compare.py` wrote `VALID` before it had a saturation check. With the
>   check added afterwards, it refuses the Computer arm. The written
>   `comparison.json` is kept as produced.
> - **Both complete collector commands missed the 15 s default bound**
>   (17.8 s and 21.8 s), under 1-minute load 13–16 with declared
>   interference.
> - **Not release evidence.**

This pair follows [`20261019T193128Z`](20261019T193128Z.md), where the SDK
set up the LayerFS arm but the timed script went through `docker exec`. Here
every command in the Sandbox goes through the public JS SDK's
`sandbox.exec`, as an agent's Bash would. `run.sh` gained an `sdk` mode that
makes three `sandbox.exec` calls through [`holder/exec.mjs`](../holder/exec.mjs):

1. report the command identity and the mount;
2. stage the frozen script under `/tmp`, check its SHA-256 and run it;
3. return the JSON and remove both files.

The holder now runs through [`holder/client.sh`](../holder/client.sh). Its SDK
home is a named volume shared with run.sh's client, so that client finds
the holder's Sandbox. The Computer arm is unchanged (`docker exec` as root).
Raw receipts are in `benchmark-results/fs-bench/20261019T194736Z/` of the
`fs-bench-sdk-main` worktree, which Git ignores.

## Route check before the pair

The first holder attempt with the shared home failed before it did anything.
The SDK refused a host folder bound into the container as `LAYERFS_HOME`,
because its owner didn't match. The home moved to a named volume. A fresh
holder then served three hand-made `sandbox.exec` calls from a separate
client process, in run.sh's command formats (about 0.4 s per call):

- identity and mountinfo (`501:20`, the FUSE line; `/workspaces` exits 4);
- staging with a hash check, without running the script;
- cleanup.

The `%q`-quoted runner environment was checked by printing it in the
container. No workload ran before the pair.

While extracting run.sh's mount check for that test, a mis-bounded `sed`
range made `eval` run part of `run.sh` in the operator's shell. Its writes
failed against `/`, and only an empty temp file was created; it was checked
and removed.

## Limits on reading these numbers

- **INCOMPLETE pair.** Two Computer rows are censored. This pair can't
  support a sum or exact ratios for them.
- **Heavier load than the earlier pairs, on both arms.** At load 8–9, the
  same binaries gave LayerFS `stat 1000 files` 924 ms, `read 64 MiB` 171 ms
  and `mkdir tree` 751 ms. Here they took 2,025, 459 and 1,800 ms. Computer
  slowed as well. This record does not attribute the change to the
  `sandbox.exec` route: the route doesn't enter the row timers, and the load
  rose from about 8 to 16.
- **Different FUSE and container profiles, by design**, as in the earlier
  records. The own-write warm rows are warm-state behaviour.
