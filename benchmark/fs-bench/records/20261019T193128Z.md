This is the third pair of the [first-pair plan](../FIRST-PAIR-PLAN.md),
collected 2026-10-19 19:31 UTC (2026-10-20 03:31 local). The LayerFS arm
now comes from latest `main` (`e5c7aaae05`), set up the way an agent would
with the public JavaScript SDK `@layerfs/sdk`. The [holder](../holder/holder.mjs)
follows the `layerfs-js-sdk` skill and `sdk/js/test/verify`:

1. `project.init` of a one-file folder;
2. `sandbox.create` on the Computer image, which installs the Store into the
   volume;
3. `branch.fork("bench", "main")`, its own Branch;
4. `sandbox.mount` of `bench`;
5. at the end, `sandbox.unmount(…, discard)` and `sandbox.close`.

The holder runs in the Linux runtime image, because SDK Store calls open the
Store in-process on Linux only (#352 F-020). [`run-holder.sh`](../holder/run-holder.sh)
starts it with the same bindings as the SDK's verify harness. This changes
the LayerFS setup route, the daemon and the daemon settings, so this is a
new pair with a new ID, not a retry. Raw receipts are in
`benchmark-results/fs-bench/20261019T193128Z/` of the `fs-bench-sdk-main`
worktree, which Git ignores. `comparison.json` hashes every raw file.

## Pre-pair check

On fresh volumes before the pair, the same holder was run twice. Both runs
were stopped by a refusal, and each fixed the holder's call order, not the
product:

- **Mount of `main` refused** `NoSuchBranch`. The holder now forks its own
  Branch, as the skill directs.
- **`list_branches` before `sandbox.create` refused** `Unsupported`. The
  Store directory didn't exist yet, because `sandbox.create` installs it. The
  holder now creates the Sandbox before its first Store call.

The third run held the mount, and the collector's view of it passed:

- `mountinfo` as above;
- as `501:20`: mkdir, write, read, `git init/add/commit` and rm;
- as root: a write, owned `501:20` as projected.

It released with `Unmounted` and `CLOSED`, and nothing was left. None of
those runs timed anything.

## Limits on reading these numbers

- **Single samples under load; the arms are noisy.** The 1-minute load was
  8–9, and another owner's container ran during the LayerFS arm. The
  Computer arm, on the same image and binaries as pair `20261019T191404Z`
  17 minutes earlier, moved by more than 2× in both directions:
  - `create 1000 files`: 880 ms there, 1,553 ms here;
  - `write 64 MiB`: 227 ms there, 94 ms here.

  The two rows Computer won here are among those that moved. Treat each row
  as one observation; a single pair cannot support a precise ratio or a
  ranking of close rows.
- **Not an A/B of the SDK route against the Rust holder.** The LayerFS
  daemon, its settings, the setup route and the host load all changed
  between pairs. This record doesn't attribute any row change to one of
  them.
- **Different FUSE and container profiles, by design.** Computer has a
  larger `max_read`, auto_cache, `relatime` and a privileged container.
  LayerFS has a smaller `max_read`, no writeback, `noatime` and the SDK's
  narrower container. The comparison is of each system as deployed, not of
  identical kernel settings.
- **Warm-state rows.** The three own-write warm rows measure warm-state
  behaviour, not cold reads.
- **Scope.** The rows exercise zero-filled inputs, resident FUSE operations
  and native arm64 in Docker Desktop on macOS. Setup (init, create, fork,
  mount), Commit and unmount are outside the timer. A native x86-64 Linux
  host remains the route to a qualifying pair.
